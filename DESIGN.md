# Design: an IMAP/SMTP-based AI email assistant

## 1. Problem

Provider REST APIs impose throttling that doesn't fit an AI email assistant's access pattern:

- **Gmail API**: a fixed per-user "Total Query Cost" budget per minute (not raisable via support). AI rule matching multiplies cost in a non-obvious way — a single AI-matched thread can trigger a follow-up fetch of up to 50 more messages from that sender to check pattern consistency, so concurrency has to be budgeted far below what the message-fetch cost alone would suggest.
- **Microsoft Graph**: similar throttling model, different numbers.
- Both APIs require an OAuth app registration and consent flow per provider, which is also the main barrier to self-hosted use (see "OAuth complexity" below — this doesn't go away with IMAP).

Net effect: any workload that does real background processing (bulk backfill of history, continuous rule application, AI sender-pattern analysis) is fighting the API's quota system, not just the raw volume of mail.

## 2. Why IMAP/SMTP is a different regime

IMAP and SMTP are governed by a **separate limiting system** from the REST APIs, even on the same Gmail/Outlook account:

- Gmail IMAP: capped at **~15 concurrent connections** per account, plus (on Workspace) a **daily bandwidth cap** (~2,500 MB download / 500 MB upload per day) — no per-minute request-cost throttle at all.
- This means steady-state AI processing (read new mail, evaluate rules, occasionally send) is essentially unconstrained day-to-day; the only place the daily bandwidth cap could bite is a very large one-time historical backfill (years of full message bodies) on a single account.
- **Caveat**: authenticating IMAP/SMTP against Gmail or Outlook still requires **XOAUTH2** — an OAuth2-based SASL mechanism. This does **not** eliminate the Google Cloud / Azure AD app registration and consent flow; it only changes which protocol the resulting token is used with. For generic/self-hosted IMAP servers (anything not Gmail/Outlook), plain username+app-password auth is enough, which is actually a simplification.

## 3. Prior art check

Before committing to build this, existing open-source AI email assistants were checked for whether any of them already do this for Gmail/Outlook specifically:

- **Aomail** (aomail-ai/aomail-app) advertises "connects to Gmail, Outlook, or any IMAP service," but its actual Gmail/Outlook integration (`backend/aomail/email_providers/google/*`, confirmed via source search) uses the Gmail REST API (`googleapiclient`), not IMAP. Its "any IMAP service" claim applies only to third-party/generic mail providers, not Gmail or Outlook — so it does not solve this specific problem.
- No other candidate found comes close to inbox-zero's scope (rules engine, AI drafting, digests, multi-account).

Conclusion: this is a green-field problem worth building, not a "go use X instead" situation.

## 4. Architecture

### 4.1 Ingestion (IMAP)

- One persistent **IMAP IDLE** connection per connected mailbox for near-real-time new-mail notification (the IMAP equivalent of Gmail's Pub/Sub push watch — and notably, doesn't expire/need renewal the way a Gmail watch subscription does). Verified against a real Gmail account: a message appended while idling triggered a sync within roughly 15-20 seconds -- not instant, but well within what a background assistant needs, and far better than the polling this replaces. Implementation note: the IDLE client library's "wait for activity" promise only resolves on its own periodic renewal timer, not on each individual server push -- the actual per-message trigger is an event the library emits as pushes arrive, handled separately from that promise.
- A local **mirror** of message metadata (and, lazily, bodies) in Postgres, so rule/AI evaluation reads from the local mirror instead of re-fetching from the server on every run. This is what actually kills the "hidden extra API cost per AI match" problem — sender-pattern analysis becomes a local DB query, not 50 more IMAP fetches.
- **Gmail-specific IMAP extensions** (`X-GM-LABELS`, `X-GM-THRID`, `X-GM-MSGID`) are used when talking to Gmail, to preserve label and thread semantics equivalent to what the REST API exposes today. These are Gmail-only; a generic IMAP provider falls back to plain folder/UID semantics.
- Connection budget: cap concurrent IMAP connections per account well under the ~15 limit, shared between the IDLE connection and any active sync/backfill connections.

### 4.2 Outbound (SMTP)

- Sending goes over SMTP. Unlike the REST APIs, plain SMTP does **not** automatically save a copy to Sent — the client must `APPEND` the sent message to the Sent folder itself, with correct `In-Reply-To`/`References` headers so IMAP thread linkage matches what the REST API would have produced. Verified against a real Gmail account: send + append both confirmed (delivery to INBOX, and a byte-identical copy in Sent).
- The Sent folder must be located via the **SPECIAL-USE** extension (`\Sent` flag), not a hardcoded path — confirmed necessary in testing, since a real account's Sent folder can be locale-dependent (`[Gmail]/Sent Mail` in English, `[Gmail]/Gesendet` in German, etc., not a fixed string).

### 4.3 Background processing

- Same shape as the lesson learned from inbox-zero's bulk-run feature: low concurrency per account, pacing between page fetches, bounded lookahead (prefetch depth capped at 1) so memory stays bounded regardless of mailbox size. Those constraints came from real production incidents there and carry over directly.
- Rule/AI evaluation runs against the local mirror, decoupled from the IMAP sync process — sync failures or slowdowns don't block rule processing, and vice versa.

### 4.4 Data model (sketch)

- `Account` — IMAP/SMTP host, auth method (XOAUTH2 token ref vs app-password secret ref), provider type (`gmail` | `outlook` | `generic`).
- `Mailbox` / `Folder` — server-side folder, mapped to a label for Gmail.
- `Message` — mirrored metadata + lazily-fetched body, `uid`, Gmail `thrid`/`msgid` when applicable.
- `Rule`, `Job` — carried over conceptually from inbox-zero's model; not yet decided whether to port code or reimplement.

## 5. Decisions (settled)

1. **Tech stack**: Node.js/TypeScript, `imapflow` for IMAP, `nodemailer` for SMTP, Postgres + Prisma for the local mirror. Auth, incremental sync, IDLE push, and SMTP send + Sent-folder append are all built and verified live against a real Gmail account.
2. **UI/app shape**: full web app (Next.js, matching inbox-zero's shape), not a CLI-first or lighter-service approach. Repo restructured into an npm workspace monorepo: `packages/core` (the ingest/sync/send logic above, importable, not just runnable as scripts) and `apps/web` (the Next.js app). First slice (a page listing synced messages, reading live from the shared Postgres DB) built and verified running.
3. **Code reuse**: rebuild fresh rather than port inbox-zero's rules/AI-matching code — inbox-zero's logic assumes its own API-based data model and Prisma schema, which don't match this project's local-mirror shape closely enough to be a clean port. Reference its approach conceptually where useful, but write new code against this schema.
4. **MVP scope**: single Gmail account, read + rule-match + send, no multi-account/multi-provider yet. Confirmed.

## 6. Sync scope: recent-history default, full backfill on demand

- A mailbox's **first** sync only fetches messages from the last `SYNC_BACKFILL_DAYS` (default 30; `all`/`0` for full history), via IMAP's `SINCE` search combined with the UID range. Steady-state `sync`/`watch` are unaffected -- they always pick up new mail going forward regardless of this setting, since it only bounds the initial catch-up.
- `Mailbox.backfillBeforeUid` marks the boundary of what's *not* synced yet; `Mailbox.fullyBackfilled` is `true` once nothing's left. `npm run backfill` fetches everything below that boundary, working backward in paced batches (200 UIDs/batch, 500ms apart -- reusing the pacing lessons from the inbox-zero bulk-run feature) until caught up. Safe to interrupt: progress is persisted after every batch, so it resumes where it left off.
- Verified live: a 7-day-bounded first sync against an isolated test mailbox correctly set the boundary, and a capped 2-batch backfill run correctly walked further back and persisted state, matching a hand-computed expectation (not just "it didn't crash" -- exact counts and boundary values checked).
- The web app surfaces backfill status read-only (a line on the homepage when older mail is available); a toggle/button to trigger a full backfill from the UI is intentionally deferred, not yet built.

## 7. Rules engine

- `Rule.conditions` (optional): JSON array of `{field, operator, value}`, zod-validated, all AND-combined -- no OR/grouping yet. Fields: `fromAddress`, `fromName`, `subject`, `labels`. Operators: `contains`, `equals`, `startsWith` (labels always does an exact-match-against-any-label check, since Gmail labels are discrete strings, not free text).
- `Rule.aiPrompt` (optional): a natural-language condition evaluated via a local LLM (Ollama's `/api/chat`, OpenAI-style). At least one of `conditions`/`aiPrompt` must be set. When both are set, `conditions` acts as a cheap pre-filter before the AI call -- correct even without cost pressure (Ollama has no external quota), since a local LLM call is still far slower than an in-process field check.
- Metadata-only for AI matching so far (subject + sender, no body) -- message bodies aren't synced yet (see risk below), so match quality is bounded until that exists.
- `RULES_AI_MAX_PER_RUN` (default 200) caps AI evaluations per rule per run, so a rule with a large untouched backlog doesn't turn one run into a multi-hour AI sweep -- the rest is picked up next run, same idea as the sync cursor. AI calls run at limited concurrency (3) against the local Ollama server.
- `RuleMatch` records which rule matched which message, unique per (rule, message), so `npm run rules:run` is idempotent and cheap to re-run after every sync.
- **Body sync (lazy)**: `Message.bodyText`/`bodyFetchedAt` are populated on demand, the first time a rule with an AI prompt actually needs a candidate's body -- not eagerly for the whole mailbox. `packages/core/src/body.ts` downloads the raw RFC822 source over IMAP (`client.download`) and parses it with `mailparser` for the plain-text part, capped at 20,000 stored chars (3,000 of that goes into the AI prompt). `rules:run` only opens an IMAP connection at all when some enabled rule has an AI prompt and Ollama is configured -- a purely deterministic rule set never touches the network.
- Verified live against real synced mail and a real local Ollama server (`llama3:latest`): a "sender contains notifications@github.com" rule, a "has \Sent label" rule, and an AI rule ("is this a security alert about a new sign-in") all produced correct, spot-checked matches. For the AI rule specifically: out of 71 messages in this mailbox sharing the exact same subject ("Sicherheitswarnung"), body-fetch correctly ran for only the one message actually being evaluated (confirming the lazy-fetch scoping is real, not accidentally eager), the parsed body was genuine German account-alert text, and the AI still matched correctly with that added context.

## 8. Action execution

- `Rule.actions` (optional JSON array): a deliberately small subset of inbox-zero's action types (structurally inspired by `apps/web/prisma/schema.prisma`'s `ActionType` enum and `apps/web/utils/ai/actions.ts` in the inbox-zero fork, not ported) -- `label`, `archive`, `markRead`, `star`. All four are safe/reversible and non-sending; reply/forward/draft-email/delete are meaningfully more complex (composing content, guarding against destructive mistakes) and deliberately deferred.
- **Detection and action execution are separate, independently-idempotent steps** (`rules:run` vs. `rules:apply-actions`), each retriable on its own: `RuleMatch.actionsAppliedAt` (null until acted on) decouples "we detected a match" from "we changed the real mailbox." Matching is cheap and safe to run often; acting on the real mailbox is not.
- **Existing labels are respected, not duplicated**: `label` resolves an existing Gmail label by case/punctuation-insensitive name match (via IMAP LIST, since Gmail exposes labels as IMAP folders) before creating a new one, and refuses to target Gmail's reserved system labels (INBOX, SENT, IMPORTANT, the CATEGORY_* ones, etc. -- same guard list as inbox-zero's `GMAIL_RESERVED_LABELS`).
- **Gmail-specific quirk found via live testing, not documented anywhere obvious**: removing the `\Inbox` system label via IMAP's `X-GM-LABELS` STORE extension (`-X-GM-LABELS (\Inbox)`) is silently a no-op on this account -- the server responds `OK Success`, but the message stays in INBOX (confirmed by searching INBOX again afterward). The reliable mechanism is an IMAP `MOVE` to the SPECIAL-USE `\All` folder instead, which is what `archive` actually does. Because a move changes the message's UID, `archive` always runs last regardless of the order given in `Rule.actions`, so it can't invalidate the UID out from under a later action in the same call.
- Verified live end-to-end against real mailbox state (not just "the script didn't throw"): a scoped test rule (label + markRead + star + archive, targeting only known synthetic test messages) was applied, then independently re-verified with fresh IMAP searches -- the label existed and was reused correctly, `\Seen`/`\Flagged` were set, and the messages were confirmed actually gone from INBOX (not just believed to be, after the first attempt silently failed to archive and was caught this way).
- `npm run rules:seed-basic` adds a few common cleanup rules -- Newsletter, Marketing, Receipt, Notification -- structurally inspired by inbox-zero's default rule categories (`STANDARD_CATEGORY_SYSTEM_TYPES` in `apps/web/utils/rule/consts.ts`), with original (not copied) prompt wording. Seeded **disabled** by default, since they archive on match -- meant to be reviewed before turning on, not auto-applied blind.

**Deliberately not built yet**: reply/forward/draft-email/delete actions.

## 9. Web UI: rules management

- Full CRUD for rules at `/rules` (list with match/pending-action counts, `/rules/new`, `/rules/[id]/edit`), plus buttons to trigger `rules:run`/`rules:apply-actions` from the browser. Built as plain HTML forms posting to Next.js Server Actions (`apps/web/app/rules/actions.ts`) -- no client-side JS framework/state needed, works even without JS.
- The condition/action editors are intentionally simple rather than a dynamic add/remove list: 4 fixed optional condition rows (field/operator/value), and action checkboxes (archive/markRead/star) plus one label-name text input. Covers the full v1 condition/action set without needing client-side interactivity.
- The "run now" buttons spawn the exact same `npm run rules:run`/`rules:apply-actions` commands already used from the CLI, as a detached background process (`child_process.spawn(..., { detached: true, shell: true })` -- `shell: true` because a bare `npm` isn't directly executable on Windows, it's a `.cmd` shim), so the HTTP request returns immediately rather than blocking on IMAP/AI calls that can take a while. No live progress view yet -- refresh the page after a bit.
- **Build-time gotcha found and fixed**: `packages/core`'s internal relative imports used the TypeScript NodeNext convention (`"../labels.js"` resolving to `../labels.ts`), which `tsx` (the CLI runner) handles natively but neither Turbopack nor classic webpack do for a `transpilePackages`-included workspace package -- both fail with "Module not found," identically, so it's not bundler-specific. Fixed by switching `packages/core`'s `tsconfig.json` to `"moduleResolution": "bundler"` and dropping the `.js` extension from the handful of relative imports actually reachable from the web app (`rules/actions.ts` -> `../labels`, `../special-use`); confirmed the CLI scripts still run correctly under `tsx` afterward (extensionless resolution works fine there too), not just that the Next.js build succeeded.
- Verified live: full create -> list -> edit (fields correctly pre-filled) -> toggle-enabled -> delete round-trip against the real database, and the "Run detection now" button confirmed to actually spawn and complete a real background process (checked via the OS process list, not just "the button didn't error"), landing the same match counts as a manual CLI run.

**Deliberately not built yet**: an action editor beyond the fixed checkboxes/single label (no OR-conditions, no reply/forward/draft-email actions since those actions don't exist yet either), a live progress/log view for triggered runs, and a UI for the backfill-window/full-backfill feature (still CLI-only, `npm run backfill`).

Goal (user request): "the same GUI visually and with almost the same features as inbox-zero" -- AI assistant chat, archive, bulk unsubscribe, etc. This is a large surface (inbox-zero's own mail client has a virtualized thread list, a streaming AI chat with tool-calling, and a real RFC 8058 one-click unsubscribe flow), so it's being built in phases rather than all at once; the user chose **visual shell first**, so every feature after this looks right from the start instead of needing a re-skin later.

- Researched inbox-zero's actual frontend stack from its real source (`C:\Users\Maxime\dev\inbox-zero`, `apps/web`), not from memory: **Tailwind CSS v3** + **shadcn/ui** (`components.json`, `style: "default"`, `baseColor: "slate"`, CSS-variable theming) on top of Radix primitives, `lucide-react` icons. The chat UI specifically uses Vercel's **AI Elements** kit (`@ai-elements/prompt-input`) over `@ai-sdk/react`'s `useChat` -- relevant when the chat phase starts.
- `apps/web` now has the same stack: Tailwind v3.4.17, shadcn `components.json` (identical config values to inbox-zero's), and the shadcn CLI's own generated `components/ui/*` primitives (button, input, checkbox, table, badge, sidebar, etc.) rather than hand-rolled equivalents -- so later features can pull in more shadcn components the same way inbox-zero does, not a divergent one-off design system.
- App shell: a collapsible sidebar (`components/app-sidebar.tsx`, using shadcn's `Sidebar`/`SidebarProvider` block) with inbox-zero's actual nav item set and icons (Inbox, Chat, Assistant, Bulk Unsubscribe, Bulk Archive, Analytics) -- items for features that don't exist yet are visibly present but disabled with a "Soon" badge, rather than omitted or dead-linked, so the target structure is visible even before each piece is built.
- Existing pages (`/`, `/rules`, `/rules/new`, `/rules/[id]/edit`) restyled onto the new system (shadcn `Table`/`Badge`/`Button`/`Input`/`Checkbox`, Tailwind utility classes) -- functionally unchanged, verified with the same create/edit/toggle/delete round-trip as before to confirm the re-skin didn't regress anything.
- Dark mode CSS variables exist (`.dark` class swap, matching shadcn's convention) but nothing toggles the class yet -- the app always renders light for now; wiring an actual theme toggle (e.g. `next-themes`) is left for later.

## 11. Mail list view (phase 2)

The Inbox page (`/`) is now an actual interactive mail list (`components/thread-list.tsx`) instead of a static table: per-row checkboxes, a bulk-select toolbar, avatar initials, unread-bold styling, relative dates, label badges, and a real **archive** action (per-row hover button and bulk toolbar button) -- both client-invoked Server Actions (`app/mail-actions.ts`) that perform a genuine IMAP move, not just a client-side hide.

- **Another Gmail X-GM-LABELS quirk found live, same family as the `\Inbox`-removal one in section 8**: Gmail omits `\Inbox` from a message's reported labels when that message is fetched *from within the INBOX mailbox itself* -- it only reports `\Inbox` when the same message is fetched from a *different* folder (confirmed by comparing the two cases directly). This meant the first version of the Inbox-view filter (`labels: { has: "\Inbox" }`) matched **zero** of the ~11,000 real inbox messages, even though it looked reasonable and typechecked -- caught immediately by loading the page rather than trusting the query, another instance of the "verify live" lesson in [[feedback-imap-idle-and-range-quirks]] applying somewhere new. Fixed by adding `Message.inInbox` (`Boolean @default(true)`), an explicitly-tracked field instead of a derived one: true on sync (a message synced from the INBOX mailbox), set false by *this app's own* archive actions (both `mail-actions.ts` and `rules/apply-actions.ts` now do this whenever an "archive" action is applied). It does not detect an archive performed outside the app (e.g. directly in Gmail) -- only reflects what this app has done, an explicit known limitation rather than an oversight.
- Verified live end-to-end, not just that the UI updated: selected and archived a real inbox message through the browser, then independently re-queried IMAP directly (a fresh `SEARCH` in INBOX for that exact subject) and got zero results, confirming the message was genuinely moved server-side and the local `inInbox` flag matches reality.
- Deliberately simplified for this phase: no message body/snippet preview (would require eagerly fetching bodies for every visible row, not just AI-evaluated ones), no thread grouping (each row is one message, not a collapsed thread), no read/star toggle actions yet (archive only), no virtualization (list is capped at 50 most-recent messages via `take`, not paginated).

## 12. Bulk unsubscribe (phase 3)

Real RFC 8058 one-click unsubscribe, per the earlier explicit decision (not a simplified manual-link-only version) -- `/bulk-unsubscribe` (`apps/web/app/bulk-unsubscribe/`), senders grouped from the local mirror with counts, sorted by volume, filterable (Unhandled/All/Unsubscribed).

- **List-Unsubscribe/List-Unsubscribe-Post are fetched as part of the regular sync** (`mailbox-sync.ts`), not lazily like bodies -- header-only IMAP fetches are cheap (no MIME/body parsing), so there's no reason to defer them. `npm run backfill-unsubscribe-headers` is a one-time paced backfill for messages synced before this existed (all ~11,000 real messages here), same "mark as checked even when absent" idempotency pattern as the body backfill.
- **`packages/core/src/unsubscribe.ts`**: header parsing (via `mailparser`, not hand-rolled regex -- see the gotcha below), an SSRF guard (`isSafeHttpUrl`: http(s)-only, resolves the hostname and rejects private/loopback/link-local ranges) before ever POSTing to a URL that came from an email header (attacker-controlled input, since anyone who can email you can put anything in `List-Unsubscribe`), and the actual one-click POST (`redirect: "manual"` -- a redirect target isn't re-validated, so it's treated as "attempted, not confirmed" rather than followed).
- **Three-tier unsubscribe mechanism, matching inbox-zero's real approach**: RFC 8058 one-click POST when advertised; otherwise a manual link handed to the browser to open (the one case this app can't fully automate); otherwise, for mailto-only senders, an actual unsubscribe email sent via the account's own SMTP (inbox-zero's own approach also falls back to a link/mailto the user handles themselves for the manual case -- sending it automatically via our already-working SMTP integration is a small addition beyond that, not a port).
- **Found and fixed via live testing (not docs, again)**: `mailparser`'s header parsing has generic, undocumented-anywhere-obvious handling for the entire `List-*` header family -- it groups every `List-X` header under one `list` object keyed by the part of the name after `List-` (so `List-Unsubscribe` -> `list.unsubscribe`, `List-Unsubscribe-Post` -> `list["unsubscribe-post"]`), each holding an already-parsed `{ url, mail, name, id }` shape. The first implementation looked for `parsed.headers.get("list-unsubscribe")` (the literal header name) and got `undefined` for every message -- **0 of the first ~11,000 backfilled messages got any unsubscribe data**, despite real senders (confirmed LinkedIn, Swisscom, Digitec, etc.) clearly having the header when the raw bytes were inspected directly. Caught by checking the actual data distribution after the first backfill run rather than assuming a clean exit meant it worked; fixed by reading `parsed.headers.get("list")` and its nested shape (confirmed by direct inspection, not documentation, since this shape isn't documented anywhere obvious either). Re-running the backfill after the fix produced a realistic distribution (1,698 one-click, 352 link-only, 306 mailto-only, 8,657 with none, out of ~11,000 real messages) -- a strong signal the fix is real, not another silent failure.
- Same bundler-resolution issue as sections 9/11 turned up again in a newly-reachable file: `smtp.ts` (pulled in via this feature's mailto-fallback path) still had the old `.js`-suffixed relative import to `special-use.ts`; fixed the same way (drop the extension, since `packages/core`'s `tsconfig.json` is on `"moduleResolution": "bundler"`). Worth remembering this class of bug can resurface any time a previously CLI-only core file becomes reachable from the web app for the first time.
- Verified live: real senders (LinkedIn, Swisscom, Digitec, and others) render correctly with the right unsubscribe-method badge; the actual one-click POST/manual-link/mailto-send action itself was deliberately **not** exercised against a real vendor in this session, at the user's request (they'll test that step themselves once everything else is finished) -- so unlike the rest of this project, the final unsubscribe action itself is unverified beyond code review and the SSRF-guard/parsing logic being independently correct.

## 13. AI Assistant Chat (phase 4)

A conversational assistant at `/chat` (`apps/web/app/chat/`, `apps/web/lib/ai/tools.ts`, `apps/web/app/api/chat/route.ts`) -- streaming tool-calling chat over the Vercel AI SDK v7 (`streamText`/`useChat`) and the local Ollama server, using inbox-zero's actual `ollama-ai-provider-v2` dependency as the provider (confirmed inbox-zero itself already runs a provider-agnostic `streamText`-based chat backend, not a Gmail/OpenAI-specific one -- this is an upgrade path it already proves viable, not a novel architecture).

- **v1 tool set is deliberately small**: `listRules`, `createRule`, `searchInbox` -- read the rules table, create a new rule (conditions and/or AI prompt, optional actions), and search the local mail mirror by sender/subject substring. No send/archive/reply tools yet, unlike inbox-zero's ~20 Gmail-API-backed tools -- those need real guardrails around an LLM autonomously mutating a mailbox that this first pass doesn't have.
- **Single persistent thread per account** (`Chat` has a unique `accountId`; `ChatMessage` stores `role`/`parts` JSON) -- no multi-thread history, rename, or delete yet, unlike inbox-zero's multi-thread sidebar. History reloads correctly from Postgres on page refresh (verified live).
- **UI**: Vercel's **AI Elements** registry components (`@ai-elements/conversation`, `message`, `prompt-input`, `tool`, `loader`) installed via `npx shadcn@latest add @ai-elements/... --yes` against the same registry inbox-zero itself uses (`registry.ai-sdk.dev`). One component (`response.tsx`, a thin `Streamdown` wrapper) 404'd at the registry and was hand-copied from inbox-zero's real source instead of guessed.
- **Zod v3/v4 cross-version gotcha**: `packages/core`'s rule schemas (`ruleConditionsSchema`/`ruleActionsSchema`) are zod v3; `apps/web` is forced onto zod v4 by `ollama-ai-provider-v2`'s peer dependency (confirmed v3 can't be pinned back -- `npm ls zod` showed an unresolvable conflict). Composing a v3 schema instance directly inside a v4 `z.object(...)` type-checks but silently degrades the property's inferred type to `unknown`. Fixed by hand-duplicating fresh v4-native shapes for the AI SDK's `inputSchema` (kept in sync by hand with core's real shapes), while the *actual* validation before any database write still goes through core's authoritative v3 schemas via `.parse()` inside each tool's `execute()`.
- **Critical bug found via live testing, not typecheck**: the first working version called the tool correctly but the chat UI hung forever afterward with no visible response. Root cause -- AI SDK v7's `streamText` defaults to a single step (`stopWhen: stepCountIs(1)`); without an explicit `stopWhen`, the model is never invoked a second time to turn a tool's result into a final text answer, so the stream just ends after the tool call with nothing to show. Fixed by adding `stopWhen: stepCountIs(5)`. Not caught by typecheck (it's a runtime/behavioral default, not a type error) -- only surfaced by actually sending a message and watching the response never arrive.
- **Also found live**: the configured `OLLAMA_MODEL` (`llama3:latest`) doesn't support tool-calling at all on this Ollama server (`ollama-ai-provider-v2` surfaced a clear `400` -- `"...does not support tools"` -- in the server logs, not a silent failure). Switched `OLLAMA_MODEL` to `qwen3:8b`, the only model on the server whose `/api/tags` capabilities list includes `"tools"`. This env var is shared with the existing AI rule-matching feature (section 7); `qwen3:8b` supports plain completion too, so both features use one model going forward.
- Verified live end-to-end against the real database and real Ollama server: `listRules` and `searchInbox` both returned genuine data (real rule match counts, real LinkedIn message subjects/senders from the synced mailbox) with correct natural-language summaries following each tool call; `createRule` created a real row in Postgres, confirmed present on the `/rules` page with the right conditions/actions, then deleted as a test artifact. Chat history (user message, tool-call part, tool-result part, final text part) all persisted and reloaded correctly across a full page refresh.

**Deliberately not built yet**: multi-thread history (rename/delete/new-thread), mutating tools (archive/label/send from chat), attachments, and a model/provider picker in the UI (Ollama model is still only configured via `.env`).

## 14. Bulk archive by sender (phase 5)

`/bulk-archive` (`apps/web/app/bulk-archive/`) -- senders ranked by how many of their messages are still sitting in the inbox, with per-sender and multi-select bulk archive. Researched inbox-zero's real implementation first (`apps/web/app/(app)/[emailAccountId]/bulk-archive/` and `quick-bulk-archive/`) per the earlier "recycle what's portable" instruction, and found its actual shape doesn't transfer directly:

- **inbox-zero's Bulk Archive is AI-category-grouped, not sender-grouped** -- both its variants (an AI-categorization-based one and a heuristic-confidence-based one) require a categorization pipeline this project doesn't have. What *is* structurally close to what this project needs is inbox-zero's own **Bulk Unsubscribe** page (flat sender list ranked by volume) -- so this feature is modeled on this project's own `/bulk-unsubscribe` (`SenderTable.tsx`) and `/` (`thread-list.tsx`'s bulk-select toolbar) instead, not a port of inbox-zero's Bulk Archive component.
- **inbox-zero's actual archive execution is a large, Gmail-specific client-side "mutation outbox"**: an IndexedDB-backed, lease-claimed, cross-tab-synced optimistic queue (`MailMutationOutboxManager`) built to handle Gmail's async/offline semantics at thread granularity. Deliberately not ported -- this project's `apply-actions.ts`/`mail-actions.ts` already does real, synchronous IMAP MOVE per message over one held connection, which is simpler and sufficient for IMAP's request/response model. The only thing carried over conceptually from inbox-zero's version is the *numeric* batch-size discipline (it caps at 500-1000 messages per action), not any of the actual queueing code.
- **`apps/web/app/bulk-archive/actions.ts`**: `listArchiveCandidates()` -- senders ranked by `inboxCount` (messages still `inInbox = true`), `HAVING inboxCount > 0` so fully-archived senders drop off the list entirely rather than sorting to the bottom (unlike Bulk Unsubscribe's `listSenders`, which ranks by total historical volume regardless of inbox state -- these are different questions, so a different query, not a shared one). `archiveSenders(fromAddresses)` looks up every still-inboxed message across the given senders and archives them all through one call to `mail-actions.ts`'s existing `archiveMessages` -- reusing the same IMAP MOVE-to-`\All` logic (and its `inInbox = false` update) as the Inbox page's own archive action, rather than a second implementation.
- **UI**: `SenderArchiveTable.tsx` combines the bulk-select toolbar pattern from `thread-list.tsx` (checkbox-all, "N selected" + one bulk action button) with the sender-row layout from `SenderTable.tsx` (name/address, right-aligned counts, per-row action button) -- both patterns already proven in this codebase, not reimplemented from scratch.
- Verified live against the real mailbox, both paths: archived a real low-volume sender (10 messages) via the per-row button, then two more via multi-select bulk archive (10 + 10 messages) -- in both cases confirmed via a direct Postgres query (`inInbox = false` for all archived messages) *and* a fresh, independent IMAP `SEARCH` in INBOX for that sender (zero results), not just the UI updating or the DB row changing. The row disappearing from the list after archiving is also confirmed correct behavior, not a bug: the `HAVING inboxCount > 0` filter is what removes it.

**Deliberately not built yet**: no "archive all older than X" or age-based filtering (inbox-zero doesn't have this either, so not a gap relative to it), no per-sender message preview before archiving, no undo, no progress indicator for a very large sender's archive (a sender with hundreds/thousands of inboxed messages archives synchronously and sequentially -- same simplification as every other action-execution path in this project so far, revisit if a real sender's volume makes this noticeably slow).

## 15. Analytics (phase 6)

`/stats` (`apps/web/app/stats/`) -- four widgets, all computed from the local Postgres mirror, no live Gmail calls at page load. Researched inbox-zero's real Analytics implementation first (`apps/web/app/(app)/[emailAccountId]/stats/`) to see what transfers.

- **Mail volume over time, top senders, rule-match counts**: directly portable *patterns* from inbox-zero's `StatsSummary`/`EmailAnalytics`/`RuleStatsChart` -- all three of inbox-zero's real equivalents already read from a local mirror table (not live Gmail calls), so the query shape carries over cleanly onto this project's own `Message`/`Rule`/`RuleMatch` schema. Rendered with **Recharts** (`recharts@2.15.4`, the same version and the same shadcn `components/ui/chart.tsx` wrapper inbox-zero uses) -- newly added to this project, `npx shadcn@latest add chart`. The chart color tokens (`--chart-1`.."--chart-5"`) weren't auto-added to `globals.css` by that install in this project's Tailwind v3 setup, so they were added by hand (standard shadcn default palette, light + dark).
- **Response-time analytics deliberately not built**: inbox-zero's real version isn't actually local-mirror-only either -- it calls the Gmail API live (paginated sent-message fetch + per-thread lookups) with only a cache table, not true precomputation. Since it isn't the fully-portable local-only pattern the other three widgets are, and a from-scratch IMAP-thread-based reply-detection design is real additional work, it's deferred rather than rebuilt now.
- **`EmailActionsAnalytics` (archived/deleted-per-day) also skipped**: inbox-zero's real version depends entirely on Tinybird, an external analytics service this project has no equivalent of and isn't taking on as a dependency.
- **Sender categorization is new, not ported**: inbox-zero's real categorization is AI-driven (`aiCategorizeSender`), persisted per-sender (`Newsletter.categoryId`), and only runs as a user-triggered background batch -- its actual category set (confirmed from `apps/web/utils/categories.ts`) is `Other/Newsletter/Marketing/Receipt/Notification` as the implemented tier (a second, more granular tier -- Banking/Legal/Investor/Personal/Work/Travel/Support/Events/Educational/Health/Government -- exists in its source but is commented out/never wired up, i.e. genuinely stubbed, not just undiscovered). This project reuses the same five-category set (also already the exact names `rules:seed-basic` uses) but computes it with a **static heuristic only** (`apps/web/lib/analytics/categorize-sender.ts`: regex over sender address/name/last-subject, plus whether the sender has ever sent a `List-Unsubscribe` header -- a strong bulk-sender signal already in this project's schema from the Bulk Unsubscribe feature) -- no AI/Ollama call per sender, computed fresh on every page load rather than persisted. Deliberately no AI fallback for v1: classifying ~300 senders through a local Ollama model sequentially on every page load would be far too slow, and inbox-zero itself never does this inline either (only as an explicit user-triggered batch) -- so skipping it isn't a regression relative to the real feature.
- **A real ordering bug found via live testing against actual data, not synthetic examples**: the first version checked "has a `List-Unsubscribe` header" before checking notification-style keywords, so `notifications@github.com` (which does carry an unsubscribe header) was classified as "Newsletter" instead of "Notification" -- caught by tracing the heuristic against this account's own real GitHub-notifications sender (already independently known, from the AI-chat testing in phase 4, to have exactly 19 matched messages) rather than trusting the chart's shape looked plausible. Fixed by checking the keyword-specific patterns (Receipt, Notification) before the unsubscribe-header fallback (Newsletter/Marketing), not after -- a sender can legitimately be both transactional/notification mail *and* RFC-8058-compliant.
- **Known heuristic limitation, not fixed for v1**: the keyword patterns are English-only regex (`receipt`, `invoice`, `notif`, etc.), so a sender like `noreply@uber.com` / "Uber Belege" (German for "receipts") falls through to "Other" instead of "Receipt" despite being an obvious receipt sender to a human reader -- a real, visible gap in a genuinely multilingual mailbox (this account has significant German/French mail), not something to paper over as solved.
- Verified live against the real mailbox and cross-checked against already-known ground truth from earlier phases, not just "the charts rendered something": the Rule-matches chart's bars for GitHub notifications/Security alert (AI)/Sent by me exactly reproduced the 19/1/327 match counts already independently confirmed via the AI chat feature in phase 4; the top-senders chart reproduced the same real sender list/ordering seen in Bulk Archive; a direct Postgres query confirmed the category-breakdown query's top-300-sender window matches the same 300-row cap used elsewhere (Bulk Unsubscribe).

**Deliberately not built yet**: response-time analytics, action-log-based archived/deleted-per-day analytics (no Tinybird equivalent), AI-based category refinement, persisted/cached categorization (recomputed on every page load -- fine at 300 senders, would need revisiting at much larger scale), and a UI to correct a sender's category by hand.

## 16. Mail list message snippets (phase 7)

The Inbox list (section 11) now shows a trailing preview snippet after each message's subject, matching real email-client convention (Gmail/inbox-zero both do this) -- picking up the biggest visible remaining gap now that the sidebar's full feature set is built.

- **Split into a fast path and a lazy path, not one blocking fetch**: `page.tsx`'s server-rendered query now also selects `bodyText`/`bodyFetchedAt` and derives a snippet for any message that's already been lazily body-fetched by something else (e.g. an AI rule prompt evaluating that message earlier) -- free, no IMAP call, shows up on first paint. For the (usually larger) remainder with no cached body yet, `ThreadList` calls a new server action, `fetchMissingSnippets` (`apps/web/app/mail-actions.ts`), once on mount, which reuses the exact same lazy body-fetch core (`ensureMessageBody`, from `packages/core/src/body.ts`, newly exported as `@imap-ai/core/body`) that AI rule matching already uses -- a message fetched here is then also already cached for a later AI-prompt evaluation of the same message, and vice versa, not two separate caches. Doing this client-side after mount rather than inline in the server render is what keeps first paint fast even on a mailbox where nothing's cached yet (up to 50 sequential IMAP downloads, confirmed to take ~30s in testing -- clearly too slow to block the initial page load on).
- Same bundler-resolution issue as every previous phase that's newly exposed a `packages/core` file to the web app for the first time: `body.ts`'s `./db.js` import needed the extension dropped before it would resolve through Next's bundler, exactly like `labels.ts`/`special-use.ts` before it. Fixed proactively this time (checked for it immediately, rather than waiting to hit the error) given how consistently this class of bug has recurred.
- Both the always-there path and the lazy-fetch path render through the same trailing-snippet UI (`Subject — snippet`, muted color regardless of read/unread state, single truncated line rather than a second row -- matches this project's existing compact single-line-per-message list convention rather than switching to Gmail's two-line layout).
- **Dev-mode-only rendering gotcha found and diagnosed, not actually a bug**: in `next dev`, React Strict Mode double-invokes the mount effect (mount → cleanup → remount), so the first `fetchMissingSnippets` call's own state update gets discarded via its cancellation guard even though the underlying IMAP fetch and Postgres write it triggered complete for real; the second (non-cancelled) invocation then finds nothing left to fetch and returns an empty map, so the UI can look like nothing happened even though the data is now genuinely cached. Diagnosed by checking Postgres directly (`bodyFetchedAt`/`bodyText` were in fact populated) and confirming a full page reload immediately showed the snippets, both via `get_page_text` (proving the DOM had the real text and the earlier "no visible change" screenshots were misleading truncation, not a missing snippet) and directly against the database -- not assuming the first inconclusive screenshot meant a real bug. This is a Strict-Mode-in-dev artifact specifically; production (`next build`) doesn't double-invoke mount effects, so this doesn't affect a real deployment.

**Deliberately not built yet**: no skeleton/loading state while a snippet is still being fetched (the row just shows subject-only briefly, then updates), no snippet for messages outside the visible 50 (matches the mail list's existing no-pagination scope), no retry for a body fetch that failed (logged and skipped, same as the AI-rule-matching path's existing behavior).

## 17. Chat can now propose an archive, with confirmation bypassing the model (phase 8)

Chat's tool set gained one capability aimed at the mutation gap flagged since phase 4 ("no send/archive/reply tools yet ... those need real guardrails"): the ability to archive a sender's inboxed mail from a conversation. How it actually works is not what was originally attempted.

- **First attempt: the AI SDK's built-in `toolApproval` mechanism.** AI SDK v7 has a real, documented, non-experimental tool-approval subsystem (`streamText({ toolApproval: { toolName: "user-approval" } })`, `useChat().addToolApprovalResponse({ id, approved })`, and `ToolUIPart` states `approval-requested`/`approval-responded` that the installed AI Elements `tool.tsx` already had UI labels for, unused, since phase 4). This looked like the intended, correct way to gate a mutating tool -- pause the tool call, render Approve/Deny in the UI, only call `execute()` after approval.
- **Found broken via live testing, not assumed to work because it typechecked and matched the documented API shape**: clicking Approve updated the chat UI's local state correctly (`approval-responded`), but the *server* never actually re-invoked the tool's `execute()` -- instead, on the next request, the model just generated a plain-text claim that it had "initiated the archive," with no `tool-input-available`/`tool-output` in the raw SSE stream backing that claim (confirmed by reading the actual network response body, not just the rendered UI). Direct Postgres and fresh-IMAP-search checks confirmed nothing was actually archived. **A model confidently lying about having performed a real mailbox mutation is a worse failure mode than doing nothing** -- this was not shipped.
- **Rebuilt without the SDK's approval subsystem**: `archiveSender` (`apps/web/lib/ai/tools.ts`) is now a plain, always-auto-executed, read-only tool -- it only counts how many inboxed messages a sender has and returns that count, and its description explicitly tells the model never to claim mail has been archived just because it called this tool. The actual mutation happens via a real "Confirm Archive" button rendered in the chat UI (`chat-client.tsx`) that calls the existing `archiveSenders()` bulk-archive server action **directly**, completely bypassing the model and the conversation loop for the execution step. This is less "sophisticated" than the SDK mechanism but is simple enough to fully verify, and doesn't depend on a subsystem this project has now directly observed being unreliable.
- **A second, unrelated bug surfaced by the first fix attempt**: after wiring up `toolApproval`, the persisted single-thread chat history ended up with an orphaned tool-call (approval requested, never resolved to an output) from the broken flow. Once `toolApproval` was removed, every subsequent request in that thread failed outright with `AI_MissingToolResultsError` (`convertToModelMessages`/`streamText` refusing to process history with a tool-call that has no matching result) -- the *entire chat feature* was unusable until the poisoned history was cleared (`DELETE FROM "ChatMessage"`, safe here since it was this session's own test content, not real user conversation). Worth remembering for chat's actual multi-user/production future: an interrupted or errored tool-approval flow can leave unrecoverable history behind with the current schema, since there's no per-message repair/edit path yet.
- **A third bug, this one just a prompt-tuning gap**: the first live test of the redesigned tool had the model call `createRule` instead of `archiveSender` for "Archive all mail from X" -- a reasonable-sounding but wrong interpretation (creating a persistent rule instead of doing a one-time archive), silently creating a real rule the user didn't ask for in those terms. Not a safety bug (an unrun rule does nothing), but a real UX defect, caught by watching what tool actually got called rather than just checking the response looked plausible. Fixed by explicitly telling the model in both the system prompt and `archiveSender`'s own tool description that a one-time "archive mail from X" request should use the lookup tool, not `createRule` -- rules are for the user explicitly asking to set up ongoing automation.
- Verified live end-to-end after all three fixes, against the real mailbox: asked chat to archive a real one-message sender, confirmed the model correctly called `archiveSender` (not `createRule`) and reported the count without claiming anything was archived yet, clicked the real Confirm Archive button, and independently verified via a direct Postgres query (`inInbox = false`) and a fresh IMAP `SEARCH` (zero results) that the message was genuinely moved -- not just that the chat UI said so.
- **Known limitation, not fixed for v1**: the "Confirm Archive" button's clicked/archived state lives in client-side React state, not the persisted chat history -- reloading the page after confirming makes the button reappear on that same tool call. Clicking it again is harmless (re-querying `inInbox = true` for that sender now correctly finds nothing left to archive and reports 0), just a minor rough edge, not a correctness bug.

## 18. No-Reply, and a retroactive fix to three already-shipped features (phase 9)

`/no-reply` (`apps/web/app/no-reply/`) -- threads where the most recent message is one you sent, i.e. you're still waiting on a reply. Identified as the best next port after a fresh research pass on inbox-zero's remaining sidebar features (Reply Zero, Cold Email Blocker, Smart Categories, No-Reply, Quick Bulk Archive, Deep Clean were all surveyed; Meetings/Calendars/Attachments/Integrations were ruled out outright as needing Gmail/Slack/Calendar OAuth scopes or external paid services IMAP has no path to). Confirmed via inbox-zero's real `api/user/no-reply/route.ts` that its actual implementation goes through a generic provider abstraction, not a Gmail-only call -- genuinely close to a straight port.

- **New field needed**: `Message.toAddress`/`toName` (migration `20260915134548_to_address`) -- `fromAddress` on a sent message is our own address, not who we sent it to, so showing a recipient needs the envelope's "to", which the IMAP `FETCH` in `mailbox-sync.ts` already requested (`envelope: true`) but never stored. Now populated going forward on every sync; `npm run backfill-to-address` is a one-time backfill for sent mail synced before this existed (same idempotent-batch pattern as `backfill-unsubscribe-headers`, scoped to just `\Sent`-labeled messages rather than the whole mailbox -- much smaller, 326 messages here vs. ~11,000).
- **Query**: one thread = one row via `DISTINCT ON ("gmailThreadId") ... ORDER BY "gmailThreadId", date DESC` (Postgres's "latest row per group" idiom, already used elsewhere in this codebase), then filtered to threads whose latest message carries `\Sent`. A thread with only one message -- true cold outreach nobody's ever replied to -- counts too, matching inbox-zero's own definition.
- **A real, previously-shipped bug found and fixed while building this**: the No-Reply query initially returned zero rows even though 326 real sent messages existed. Root cause -- inside a `$queryRaw` template literal, `'\Sent'` (a single backslash) is not a recognized JavaScript escape sequence, so the template literal silently cooks it down to `'Sent'` (backslash dropped) before the query text ever reaches Postgres, which then matches nothing. Confirmed directly: `` `'\Sent'` `` has no backslash character in it at runtime (checked via `charCodeAt`), while `` `'\\Sent'` `` correctly produces one. **This exact mistake was already shipped in three earlier features**, not just a risk in the new one: `getVolumeOverTime`'s "sent" bucket and the self-sent-mail exclusion in `getTopSenders`/`getCategoryBreakdown` (all in `apps/web/app/stats/queries.ts`), and the `'\Seen'` unread-count filter in both `bulk-archive/actions.ts` and `bulk-unsubscribe/actions.ts` -- meaning **Bulk Archive's and Bulk Unsubscribe's "Unread" column had silently always equaled the "In inbox"/"Emails" column** (since `NOT ('Sent' = ANY(labels))`/`NOT ('Seen' = ANY(flags))` compares against a string that can never appear in real data, so the `NOT` is always true), and Analytics' sent-tracking and self-sent-exclusion were no-ops the entire time those features were "verified live."
- **Why earlier verification missed it**: the affected charts/tables weren't obviously broken -- they rendered real-looking data (the Unread badge showed *a* number, just the wrong one; the volume chart's stacked total was actually still correct, since misattributing sent-as-received doesn't change the sum). Earlier verification checked that the *shape* of the output looked plausible and cross-referenced a few *unaffected* numbers (e.g. rule-match counts, which come from the ORM, not raw SQL), not the specific *values* these particular columns depended on. Caught here only because the new feature's query depended entirely on the filter actually working (zero rows is impossible to miss), which prompted comparing the app's result against a raw `psql` query with the identical-looking SQL text and a `COUNT(*)` -- and finding they disagreed.
- All four affected queries fixed (single backslash -> doubled) and re-verified live against real ground truth, not just re-reading the code: Bulk Archive and Bulk Unsubscribe now show genuinely differentiated Unread counts (e.g. a sender with 711 inbox messages and 469 actually unread, not 711/711); Analytics' Top Senders list no longer includes the account's own address; a direct `COUNT(*)` for the last-90-days sent/received split (1 sent, 368 received) confirms the volume chart's now-correct, if visually subtle, split. A code comment was added at the first occurrence (`stats/queries.ts`) explaining the trap for future edits, since it's easy to reintroduce.

**Lesson for this project's own "verify live" practice, worth remembering**: matching the *shape* of an expected result (a chart renders, a badge shows *some* number, totals look right) is not the same as verifying the *specific value* a feature's logic actually depends on. A raw SQL string embedded in a JS/TS template literal needs the same escaping scrutiny as any other string in the language -- "it's SQL, so I don't need to think about JS escaping" is exactly the trap that shipped this three times over.

## 19. Risks

- Large one-time historical backfills could hit the Workspace daily bandwidth cap on very large mailboxes -- the paced, resumable `backfillOlderMessages` design (section 6) is meant to keep any single run modest regardless of total mailbox size, but a truly enormous mailbox synced in "all" mode could still take a while.
- IMAP behavior differs meaningfully across providers (Gmail extensions are Gmail-only; other providers vary in `UIDVALIDITY` stability, folder naming, etc.) — the generic-provider path needs to degrade gracefully rather than assuming Gmail semantics everywhere.
- Storing mirrored message bodies locally increases the data-security surface compared to a stateless API pass-through — encryption at rest and a clear retention/deletion policy should be part of the design, not an afterthought.
